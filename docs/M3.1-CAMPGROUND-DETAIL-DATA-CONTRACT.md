# M3.1 — Campground Detail Data Contract

Status: FROZEN for M3 implementation

## Goal

Make `/camping/[slug]` a trustworthy public campground detail page backed by the existing Supabase schema. M3.1 defines the data contract only; later M3 steps implement presentation and interaction.

## Audit of current implementation

The current detail page already provides a useful shell: cover image, verification badge, types, name/address/summary, elevation/access/type/data facts, facilities, access, suitable-for, price summary, directions, metadata, 404 handling, and related campground cards.

However, `getCampgroundBySlug()` currently reuses the compact directory `Campground` model. That model intentionally collapses relational detail and therefore cannot represent everything required by M3.

Missing or collapsed data includes:
- full `description`
- `capacity_people`
- `access_description`
- `check_in_info`
- `good_to_know`
- all active price rows with type/label/unit/note
- all public contacts with type/label/value/primary flag
- all approved photos with alt/caption/credit/source/cover/order
- facility notes
- access notes
- verification provenance/history

## Architecture decision

Do **not** expand the directory `Campground` type into a large detail object.

Keep the existing `Campground` model as the compact directory/map/card contract. Introduce a dedicated `CampgroundDetail` contract and a dedicated detail repository query. This prevents directory/map payloads from growing as M3 gains richer content.

`getCampgroundBySlug()` will evolve to return `CampgroundDetail | null`. Related-card discovery continues to use the compact `Campground` contract.

## Public detail contract

```ts
export type CampgroundPriceDetail = {
  id: string;
  type: "entrance" | "camping" | "parking" | "tent_rental" | "equipment_rental" | "firewood" | "other";
  label: string;
  amountIdr: number;
  unit?: string;
  note?: string;
  sortOrder: number;
};

export type CampgroundContactDetail = {
  id: string;
  type: "whatsapp" | "phone" | "instagram" | "website" | "email";
  label?: string;
  value: string;
  isPrimary: boolean;
};

export type CampgroundPhotoDetail = {
  id: string;
  url: string;
  altText?: string;
  caption?: string;
  creditName?: string;
  sourceUrl?: string;
  isCover: boolean;
  sortOrder: number;
};

export type CampgroundFacilityDetail = {
  name: string;
  note?: string;
};

export type CampgroundAccessDetail = {
  vehicleType: string;
  note?: string;
};

export type CampgroundVerificationDetail = {
  status: VerificationStatus;
  verifiedAt?: string;
  sourceType?: string;
  sourceNote?: string;
};

export type CampgroundDetail = Campground & {
  description?: string;
  capacityPeople?: number;
  accessDescription?: string;
  checkInInfo?: string;

};
```

## Database mapping

### `campgrounds`
Public published row only, enforced by existing RLS.

Detail uses:
`id`, `slug`, `name`, `short_description`, `description`, `address`, `district`, `latitude`, `longitude`, `elevation_m`, `capacity_people`, `access_description`, `check_in_info`, `good_to_know`, `verification_status`, `last_verified_at`, `featured`.

### Geography
`provinces(name,slug)` and `regencies(name,slug)`.

Names are needed now; slugs are retained in the detail query design for M4 geographic navigation.

### Types
`campground_type_relations -> campground_types(name,slug)`.

### Facilities
`campground_facilities(is_available,note) -> facilities(name,slug,category,icon_key,sort_order)`.
Only rows visible under current public RLS and with `is_available=true` are rendered as available facilities.

### Access
`campground_access(vehicle_type,is_accessible,note)`.
Only accessible entries are rendered as positive access capabilities.

### Suitable for
`campground_suitable_for(label)`.

### Prices
`campground_prices(id,type,label,amount_idr,unit,note,is_active,sort_order)`.
Existing public RLS already exposes active prices only. UI must show individual rows; `priceFrom` remains a derived convenience value for cards/hero summary.

### Contacts
`campground_contacts(id,type,label,value,is_primary,is_public)`.
Existing public RLS exposes public contacts only. UI must never infer or expose non-public contacts.

### Photos
`campground_photos(id,storage_path,alt_text,caption,credit_name,source_url,is_cover,status,sort_order)`.
Existing public RLS exposes approved photos only. Public URLs are derived from the `campground-photos` bucket. Cover preference: approved `is_cover=true`, then `sort_order`, then fallback image if no approved photo exists.

### Verification
The current public schema deliberately has no browser SELECT grant/policy on `campground_verifications`. M3.1 does **not** weaken that boundary.

For M3 public trust UI, use `campgrounds.verification_status` + `last_verified_at` as the authoritative public summary for now. `source_type` / `source_note` provenance remains unavailable until a later migration explicitly defines a safe public projection or RPC. `verified_by` must not be exposed publicly.

Therefore `CampgroundDetail.verification` in M3 is populated only from public summary fields initially; source fields remain undefined.

## Derived presentation rules

- `priceFrom`: minimum active public price, otherwise `0` / “Hubungi pengelola” or “Belum tersedia” according to context.
- `image`: approved cover photo, then first approved photo, then existing fallback.
- `lastVerifiedAt`: keep current compatibility sentinel internally if necessary, but M3 UI should prefer optional/null semantics rather than displaying epoch values.
- directions URL: derive from validated latitude/longitude; never store a generated Google Maps URL in DB.
- WhatsApp/Instagram/website links: generated from public contact rows, with input normalization/validation before rendering external hrefs.
- long-form empty fields are omitted or shown with an explicit “belum tersedia” state; never invent campground information.

## Security contract

M3 detail remains public-read only.

- No service-role/secret key in browser or Next public environment variables.
- Existing RLS remains the first visibility boundary.
- Only `status='published'` campgrounds are public.
- Only active prices are public.
- Only `is_public=true` contacts are public.
- Only approved photos are public.
- `campground_verifications.verified_by` is never public.
- Do not add public access to moderation/submission data in M3.1.
- External contact URLs must be normalized before becoming clickable links.

- Current page and repository audited.
- Rich detail fields mapped to existing schema.
- Directory and detail contracts separated.
- Public visibility rules explicitly documented.
- Verification provenance does not bypass existing security design.
- No database migration required for M3.1.
