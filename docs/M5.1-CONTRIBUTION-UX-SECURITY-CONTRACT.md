# M5.1 — Community Contribution UX & Security Contract

Status: FROZEN FOR M5 IMPLEMENTATION

## Goal

Allow the IndoCampingLovers community to contribute useful campground information with low friction while keeping canonical directory data moderated and protected.

Public contributors describe what they know. They do not edit canonical database records directly.

## Entry points

### New campground
Header CTA: `Tambah Tempat` → `/tambah-tempat`.

Four-step wizard:
1. **Tempat** — name, province, regency/city, address/location.
2. **Informasi** — camping type, price, facilities, vehicle access, public contact, notes.
3. **Foto** — optional photo contribution and rights confirmation.
4. **Pengirim** — contributor name/contact, summary, consent, submit.

Before final submission, the application should warn about likely duplicate campground names in the selected geography. It must not silently merge submissions.

### Existing campground update
Detail CTA: `Usulkan perubahan` → `/camping/{campground-slug}/usulkan-perubahan`.

Contributor first selects an update category:
- general
- price
- facility
- access
- contact
- location
- operating_status
- photo

Only fields relevant to the selected category are shown.

## Submission lifecycle

```
Community form
  → server validation
  → submission row
  → pending
  → admin moderation
      → reviewing
      → approved / rejected
  → canonical data changes only through approved moderation
```

New campground uses `campground_submissions`.
Existing campground changes use `campground_update_submissions`.

Neither flow grants anonymous/authenticated browser INSERT/UPDATE/DELETE access to canonical campground tables.

## Authentication

M5 public contribution does not require a user account.

`submitted_by` remains nullable. Contributor identity is represented by the minimum fields needed for moderation/follow-up.

No public submission status page may expose submitter name/contact or raw moderation data.

## Contributor data

MVP asks for:
- contributor name;
- one practical contact channel;
- explicit acknowledgement that ICL may use the submitted information to maintain the directory.

Do not request sensitive identity documents or unnecessary personal information.

## Confirmation

Successful submission shows:
- success state;
- human-friendly reference code derived from the submission id;
- status: `Menunggu pemeriksaan`;
- explanation that submission is not published immediately;
- CTA back to directory.

The reference code is for communication, not authentication.

## Photos

Photo contribution is optional.

Requirements:
- accepted image formats only;
- file-size limit;
- contributor confirms they have the right/permission to submit;
- uploads remain pending until moderation;
- public gallery continues to expose approved photos only.

M5 photo-upload implementation must use a controlled upload path. Existing canonical photo/browser write restrictions remain in force until that path is implemented and reviewed.

## Moderation UX

Admin queue separates:
- new campground submissions;
- update submissions.

Each item shows submitted facts and contributor context needed for review.

Update moderation should present **current value vs proposed value** where practical.

Actions:
- Review
- Edit before approval
- Approve
- Reject

Approval must be explicit and idempotent. Refresh/retry must not create duplicate canonical records or repeat an approved mutation.

## Trust integration

Community approval does not automatically claim independent ICL verification.

After an accepted community update, canonical trust should normally become `community_updated` with an appropriate freshness timestamp/audit event. Independent ICL verification remains a separate moderation/verification action.

## Validation & abuse controls

Server-side validation is mandatory even when browser validation exists.

M5 implementation must include:
- payload size limits;
- allowed-field validation;
- enum/reference validation;
- URL/contact normalization where applicable;
- duplicate-submit protection/idempotency;
- basic anti-spam/rate limiting before public launch;
- safe error responses without database internals.

## Data boundary

Submission payload JSON is staging/moderation data, not a substitute for canonical relational data.

On approval, accepted values are normalized into the canonical tables already defined in M1.

Rejected submissions remain moderation records according to the future retention policy; they never become public campground content.

## Accessibility & mobile

- Wizard works on mobile first.
- Progress is visible as text as well as visual steps.
- Form controls have labels and accessible errors.
- Contributor can move backward without losing completed fields during the active flow.
- Required vs optional fields are explicit.
- Error states preserve user-entered non-file data when practical.

## Out of scope for M5.1

- Owner claim.
- Public accounts/profiles.
- Reviews/ratings.
- Booking/payment.
- Contributor leaderboard/gamification.
- Automatic AI approval.
- Automatic publication without moderation.
- Public exposure of contributor contact details.

## Acceptance for M5.1

- Public and admin flows are unambiguous.
- Canonical campground data cannot be directly mutated by contributors.
- Anonymous contribution is supported without public account requirement.
- Photo moderation boundary is explicit.
- Trust semantics are explicit.
- Security/abuse requirements are defined before implementation.
