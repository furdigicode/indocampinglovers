# M2.4 — Map Discovery

Status: requirements frozen on `develop` before implementation.

## Goal

Give users a geographic discovery mode for the same campground result set already produced by the M2 directory query engine. Map is a second presentation of directory discovery, not a separate search system.

## Product contract

- `/camping` remains the canonical discovery route.
- Default view is `list`.
- `view=map` selects Map View and is shareable/bookmarkable.
- Search/filter/sort state remains in the same URL query contract.
- For the same query, List and Map must represent the same eligible campground result set.
- Only public `published` campground data may reach Map View through existing RLS/public-read boundaries.

## Functional requirements

### 1. List / Map switch

- Add a clear `Daftar / Peta` control near the directory result summary.
- Switching view preserves q, province, regency, type, facility, access, price and sort parameters.
- Switching back to List preserves the same discovery state.
- `view` is presentation state and must not alter filtering semantics.

### 2. Map data

Each map point must have at minimum:

- campground id
- slug
- name
- latitude
- longitude
- province
- regency
- type summary
- public price-from state
- verification state

Campgrounds without valid coordinates must not crash Map View. They should be excluded from markers while the UI communicates if results exist without mappable coordinates.

### 3. Marker interaction

- One marker per mappable campground result for M2.4.
- Clicking/tapping a marker opens a lightweight campground preview.
- Preview contains name, regency/province, type when available, price-from or `Hubungi pengelola`, and verification state.
- Preview contains `Lihat detail` linking to `/camping/[slug]`.
- Marker/preview interaction must be usable with mouse and touch.

### 4. Viewport behavior

- Multiple results: fit map bounds to all mappable results with safe padding.
- Single result: center/focus the campground at a useful local zoom.
- Zero mappable results: show an intentional empty map state rather than throwing an error.
- Indonesia-wide results must produce a useful national overview.

### 5. Responsive UX

- Desktop and mobile must both support pan, zoom, marker selection and detail navigation.
- Map must have an explicit usable height rather than relying on viewport accidents.
- Map controls must not obscure primary content on small screens.
- The existing filter experience remains available in Map View.

### 6. Performance

- MapLibre and map-specific browser code must not be part of the initial List View execution path when avoidable.
- Prefer lazy/dynamic loading for Map View.
- Do not load canonical campground write capabilities into the browser.
- M2.4 may use the existing directory query/RPC architecture but must not fetch the entire national database merely to render a normal paginated List View.

## Technical direction

- Renderer: MapLibre GL JS.
- Basemap: OpenStreetMap-compatible tiles/style with proper attribution.
- No Google Maps dependency for M2.4.
- Existing PostgreSQL latitude/longitude fields remain the canonical coordinates.
- PostGIS is not required for M2.4 because radius, nearest-neighbor and viewport-area search are out of scope.

## URL examples

```text
/camping?view=map
/camping?province=jawa-barat&view=map
/camping?province=jawa-barat&type=family-camping&facility=toilet&view=map
```

## Out of scope

The following are explicitly deferred:

- `Search this area` after map pan/zoom
- radius / `near me`
- user geolocation
- nearest campground ranking
- marker clustering for large-scale datasets
- heatmaps
- drawing geographic areas
- route planning/navigation inside ICL
- PostGIS spatial search
- map-specific SEO landing pages

These require separate product/scale decisions and must not silently enter M2.4.

## Acceptance criteria

M2.4 is complete only when:

1. List/Map switching is shareable through URL and preserves active discovery parameters.
2. Map View uses the same search/filter eligibility semantics as List View.
3. Published mappable results render as markers.
4. Marker interaction exposes a useful preview and links to campground detail.
5. 0, 1 and many-result map states are safe.
6. Multiple results fit bounds and a single result focuses correctly.
7. Mobile and desktop interactions are usable.
8. Existing M2.3 List View behavior does not regress.
9. Public RLS/security boundaries remain unchanged; no browser write capability is introduced.
10. TypeScript, production build, npm security audit and GitHub CI remain green.

## QA fixture

The isolated `ICL QA` M2.3 fixture may remain temporarily during M2.4 implementation because its 30 records are useful for marker/filter QA. It must be removed using `supabase/fixtures/m2_3_directory_qa_cleanup.sql` before production data preparation.
