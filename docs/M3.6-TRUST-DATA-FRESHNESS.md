# M3.6 — Trust & Data Freshness

## Goal
Help campers understand how trustworthy and how recent campground information is without exposing moderation or verifier internals.

## Public source of truth
M3.6 uses only public-safe fields already exposed on `campgrounds`:
- `verification_status`
- `last_verified_at`

`campground_verifications`, `verified_by`, moderator notes, and internal audit history remain private.

## Public statuses
- `verified` → **Terverifikasi ICL**
- `community_updated` → **Diperbarui komunitas**
- `needs_update` / public mapping of `unverified` → **Perlu diperbarui**

## Freshness rules
Freshness is deterministic and computed from `last_verified_at`:
- no valid verification date → `unknown`
- age <= 90 days → `fresh`
- age 91–180 days → `aging`
- age > 180 days → `stale`

A campground explicitly marked `needs_update` is always presented as requiring confirmation regardless of date age.

These thresholds are a product freshness policy, not a claim that campground facts become false after a specific number of days.

## UX contract
Detail page must show a dedicated **Status & keandalan data** section containing:
1. verification status label;
2. last checked/updated date when available;
3. plain-language explanation of what the status means;
4. freshness message;
5. reminder to confirm operational facts such as price, access, facilities, and operating conditions with the manager before departure when appropriate.

The sticky summary may retain a compact trust indicator, but the dedicated section is the authoritative explanation.

## Copy intent
### Verified
ICL has checked the campground information. Still remind users that operational details can change.

### Community updated
Information includes a recent community contribution but should not imply ICL independently verified every field.

### Needs update
Information may be incomplete or outdated. Users should confirm important details before departure.

### Aging/stale
Describe age neutrally. Do not say data is wrong solely because it is old.

## Security / privacy
Never expose:
- verifier user ID/name from `verified_by`;
- internal verification notes;
- moderator notes;
- submission payloads;
- private audit history.

No RLS or browser grant changes are required for M3.6.

## Acceptance criteria
- Status copy matches the public verification state.
- Last verification date is shown only when valid.
- Freshness is deterministic from date age.
- `needs_update` produces a confirmation warning.
- Missing date has a safe unknown state.
- No private verification/audit fields are queried or rendered.
- Desktop and mobile detail layouts remain usable.
